# Skill 自演进框架 · 项目设计总结

核验日期：2026-09-09。依据为当前工作区代码（含未提交修改）、Git 历史、Skill 协议与参考格式、广州实跑产物，以及第 1 节所链接的论文原文。本文供项目汇报使用，区分代码实现、人机协作实践、设计目标与未来方向。

## 一句话定位

本项目面向城市资源检索，形成了**任务反馈驱动的 Skill 人机协同演进流程**：开发者与 Agent 分析真实任务中的问题，将可复用修复沉淀为执行协议、处理脚本、公共组件和相关测试；新场景以现有模板和公共能力为基础，补充来源适配与业务规则。

当前已实现基础教育、医疗机构和高校三个场景的检索处理链路。基础教育与医疗按行政单位输出区级工作簿及城市总表；高校先按固定名单的学校所在地筛选，再获取这些学校的校区地址，输出高校信息与异常校工作簿。高校场景不能直接解释为“穷尽所有在该市设有校区的高校”。

本文的“自演进”指任务反馈驱动的外部资产持续改进。仓库尚未实现自动分析失败、修改 Skill、对照评测并自动取舍候选版本的统一控制程序，也没有证明每次任务执行都会带来能力提升。

## 1. 论文背景与本项目的关系

这些论文从不同角度研究不更新底层模型参数的 Agent 能力改进。以下按首次预印本时间排列，表示相关研究参照，不表示逐篇直接继承或本项目已解决其开放问题。

| 论文 | 主要机制 | 本项目借鉴的思想 | 实现边界 |
| --- | --- | --- | --- |
| [Reflexion（2023-03）](https://arxiv.org/html/2303.11366v4) | 将评价反馈转为语言反思，保存到跨尝试的记忆；评价可来自规则、环境或 LLM | 利用任务反馈修正后续行为 | 当前没有统一的自动反思记忆模块；经验由开发者与 Agent 判断后沉淀 |
| [Voyager（2023-05）](https://arxiv.org/html/2305.16291v2) | 自动课程提出任务，程序在执行反馈与自验证中迭代，成功技能按描述索引入库复用 | 将反复使用的操作保存为可执行能力 | 公共函数复用已实现；自动课程和运行期技能向量检索未实现 |
| [ExpeL（2023-08）](https://arxiv.org/html/2308.10144v3) | 从跨任务成功/失败经验中抽取并更新 insights，推理时结合成功轨迹检索 | 从具体任务中识别可复用经验 | 组件抽取和模板沉淀是工程类比，未实现 ExpeL 的经验池学习算法 |
| [SkillWeaver（2025-04）](https://arxiv.org/html/2504.07079v1) | 主动探索网站，合成可复用 Python API，并生成测试参数、执行和调试 API | 对沉淀能力开展测试和修复 | 当前采用真实任务驱动的协作开发；没有自主技能提案与 API honing 控制器 |
| [EvoSkill（2026-03）](https://arxiv.org/html/2603.02766v1) | 分析失败并构建候选技能，以候选 Agent program 的验证集得分维护 frontier | 把技能改动与整体任务效果关联 | 自动候选构建、验证集选择与反馈历史驱动搜索均为未来方向 |

本项目的三个工程侧重点：

1. **资产可执行、可复用。** 执行协议（SKILL.md）、固定脚本、领域词表、参考格式、相关测试及按需配置的静态资产共同支撑任务。新增脚本增加可复用的高层操作能力，模板用于指导构建，模板本身不是可执行动作。
2. **改动与交付有检查依据。** 已有回归测试，以及分场景的预览、覆盖检查、质量报告和生成前门禁。它们约束已覆盖的错误，不等价于证明新 Skill 在独立任务集上整体变强，也未证明优于论文中的 LLM 评价器。
3. **通过公共组件与模板降低重复建设。** 地址处理、来源读取、网页采集、工作簿输出已被多个场景复用；领域差异主要放在 Skill 侧。仍有部分教育适配保留在公共层，模板也不消除新场景的业务实现工作。

论文对照用于说明研究动机与实现选择。代码分层、测试和文档管理不能直接称为已解决技能库的冲突检测、淘汰或生命周期管理。

## 2. 设计目标与总体设计

### 2.1 设计目标

- **能力可沉淀**：将真实任务中值得复用的修复保存到资产中；不是每次执行都必须改动资产，资产数量增长也不等于效果提升。
- **交付可溯源**：机构名录与原始地址采用官方证据；最终地址允许按模式进行地图核验或兜底，并标记获取方式。空地址与异常记录按场景规则保留在阶段文件或异常表中。
- **场景可复制**：新城市复用现有链路并重新检索、确认来源；新场景借助模板和公共核心减少重复实现，遇到新来源形态仍需适配。
- **改动可检查**：按改动性质配置回归测试、阶段对账与任务复核；跨任务的演进收益需要另建评测集验证。

### 2.2 关键设计决策

1. **改进对象是外部资产。** 仓库不包含底层模型参数训练流程；协议、代码、词表、测试与文档是当前迭代对象。这不表示已有控制模型版本不变的对照实验。
2. **语义判断与固定处理分工。** Agent 负责来源身份、合并/停办、学段/类别覆盖和异常复核；固定脚本负责规则驱动的解析、去重、地址路由、排序与 Excel 生成。扫描件识别和外部服务结果仍需复核。Skill 协议限制手工抄写最终记录。
3. **公共能力逐步去耦。** `official/extract` 通过 `FieldTerms` 与回调接入场景差异，地址查询支持 `poi_name_aliases`。公共层仍含 `campus_name` 读取和 MinerU 学校名称识别规则，不能宣称全层零场景语义。
4. **阶段产物构成证据链。** 来源清单、访问结果、提取计划和地址记录分别保存可追溯信息。例如地址记录有 `source_reference`、`source_nature`，访问结果有 `access_attempts`；日期按各场景字段约定保存，不要求每条地址记录都具有同一组审计字段。
5. **按场景设置检查。** 回归测试验证已覆盖规则，阶段检查核对计划或任务覆盖，交付检查拦截已定义的结果问题。部分检查由代码直接阻断，部分由 Skill 协议要求 Agent 单独执行。

## 3. Skill 架构（当前现状）

### 3.1 总体架构

```text
search_city_source/
├─ .agents/skills/                          # Skill 资产层（Codex 可直接调用）
│  ├─ query-city-basic-education/           # 政府名单型：基础教育学校
│  ├─ query-city-medical-institutions/      # 政府名单型 + 在线平台：医疗机构
│  └─ query-city-universities/              # web_search 型：高校校区地址
├─ packages/query-city-core/                # 公共包，当前版本 0.1.0，editable 安装
│  ├─ src/query_city_core/
│  │  ├─ address/                          # 城市上下文、地址规范化、地图核验与兜底
│  │  ├─ official/                         # readers / collectors / extract
│  │  ├─ web/                              # 官网页面抓取、域名现用性探测
│  │  ├─ excel_style.py / excel_output.py  # 统一工作簿格式与原子保存
│  │  ├─ access.py / host_gate.py / io_utils.py / env_utils.py
│  │  └─ assets/china_city_catalog.json    # 中国城市目录
│  └─ tests/                               # 公共能力回归测试
└─ doc/                                     # 模板、操作手册、本总结
   ├─ government-source-skill-template.md   # 政府名单类 Skill 模板（教育、医疗）
   ├─ web-search-skill-template.md          # 先名单后官网取证类模板（高校）
   └─ 基础教育查询操作手册.md / 医疗机构查询操作手册.md / 高校查询操作手册.md
```

### 3.2 一个 Skill 内部长什么样

当前 Skill 的资产可以按以下五类理解，其中静态资产按场景需要配置：

| 组成 | 作用 |
| --- | --- |
| `SKILL.md` | 执行协议：输入输出、来源口径与层级、覆盖要求、命令链、完成检查、最终回复约束 |
| `AGENTS.md` / `requirements.txt` | 代码规范与公共包版本约束；requirements 当前只列 `query-city-core==0.1.0`，不是完整环境锁文件 |
| `references/` | 各阶段 JSON 字段与来源格式约定；脚本实现相应的局部校验，不等同于统一 JSON Schema 验证器 |
| `assets/`（按需） | 固定资产，如高校 Skill 的教育部普通高校/985/211 名单 |
| `scripts/` + `scripts/tests/` | 场景入口、领域规则、记录构造、输出适配与回归测试；部分脚本包含较多业务逻辑 |

editable 安装会直接使用当前源代码；相同的 `0.1.0` 版本号不足以标识每次运行的精确代码状态，复现实验还需记录提交号、未提交改动和环境信息。

### 3.3 公共核心层

- `address/`：城市标准化与直接下级行政单位（`city.py`）、地址清洗与规范化（`normalize.py`）、高德地理编码/POI/行政区查询与最终地址决策（`verify.py`、`amap_client.py`）、批处理入口（`process.py`）。
- `official/`：官方来源读取器（HTML/Word、Excel/CSV、PDF、扫描件视觉转录 `mineru_reader`）、来源收集器（栏目链接、来源文件与 zip 安全解压、名录页同构详情页）、通用提取引擎（`inspect`/`extract`，词表由 Skill 注入）。
- `web/`：官网页面抓取与域名现用性探测；直连（urllib→curl）与浏览器兜底，访问审计。
- `excel_style.py` / `excel_output.py`：统一列序、地址输出列、来源超链接、原子保存与自动复核。
- `access.py` / `host_gate.py` / `io_utils.py` / `env_utils.py`：网络直连、同主机节流、JSON 读写、配置读取。

分层目标是让可复用能力进入公共层、领域规则留在 Skill 层。三个场景已共享主要基础能力，但仍有适配残留：`official/readers/mineru_reader.py` 的 `_SCHOOL_NAME_MARKER` 参与表格行对齐，`address/verify.py` 读取 `attributes.campus_name` 并包含校区名称匹配规则。后续通用化需连同这些行为的测试一起处理。

### 3.4 数据与证据管线（两条主链路）

政府名单型（基础教育/医疗）：

```text
city_context.json
  → <行政单位>/government_source.json（来源清单 + 完整城市上下文）
  → extraction_plan.json（inspect 生成，Agent 复核批准）
  → address_records.json（extract，去重保留异常）
  → processed_address_records.json（address.process 串行）
  → 区级工作簿 + 城市总表（build_excel）
```

官网取证型（高校）：

```text
city_context.json → city_universities.json（固定名单按城市筛选）
  → domain_batches/*.json → domain_probe_report.json → official_domain_manifest.json
  → school_results/<标识码>.json（并发抓取，原子落盘）
  → university_retrieval_results.json（覆盖校验）→ address_records.json
  → processed_address_records.json → 高校信息 + 异常校工作簿
```

两条链路共用地址记录结构。当前实现的来源模式为 `government_list` 和 `web_search`；`map_search` 仅是预留模式，代码返回 `skipped`，不执行独立地图检索。有效来源地址可直接采用，部分记录才进入地图核验或兜底，不能把“经过地址组件”写成“每条均由高德验证”。

参考文档约定阶段字段，脚本检查阶段标记和部分必填项，Agent 按协议完成语义与覆盖复核。阶段文件支持追溯，但文件存在或字段合法不能独立证明来源完整和内容正确。

## 4. 自演进机制：演进是怎么发生的

### 4.1 人机协同演进流程

```text
① Agent 按 Skill 协议调用脚本执行真实任务（城市 × 场景）
    │  暴露失败 / 缺口 / 新来源形态 / 新场景
    ▼
② 开发者与 Agent 定位问题并判断沉淀层次
    SKILL.md 协议 ｜ 领域脚本 ｜ 公共核心层 ｜ 模板与文档
    ▼
③ 开发者与 Agent 修改资产并补齐相关验证
    规则或代码改动 + 适用的回归测试 + 相关文档同步
    ▼
④ 执行相关检查并复核结果
    回归测试 / 场景阶段检查 / 交付检查；开发者与 Agent 判断是否保留
    ▼
⑤ 保存改动与证据，按需反哺公共层
    具有复用价值的部分抽取为公共能力；同步受影响模板与参考格式
    ▼
⑥ 新任务 / 新场景复用 → 回到 ①
```

这是依据提交历史和当前工具总结的协作流程，不是仓库内自动执行的控制回路。任务失败可能来自来源不可用或输入问题，未必需要修改 Skill。只有经过判断并保存为可复用资产的变化，才计入此处讨论的演进。

### 4.2 四类演进载体

1. **协议演进（SKILL.md）**：来源口径、检索层级、覆盖要求、完成检查。例如基础教育把检索起点按学段分层（高中以市级为首要层级、幼小初以区级为首要层级并要求回退），并新增 `coverage_notes` 强制说明缺口。
2. **能力演进（脚本/公共层）**：新增来源处理能力或修复规则。例如 MinerU 扫描件解析服务接入、政府查询平台分页抓取（`platform-query`，医疗场景首个落地）、地址“省实路”误判修复。
3. **验收演进（测试与门禁）**：为已识别错误补充回归用例和校验规则，将部分经验转化为可执行约束。协议中的完成要求并非全部由代码强制执行。
4. **复用范围扩展（模板/文档/字段）**：把多个场景需要的能力抽取到公共层，沉淀模板和操作手册。工程复用已有实例；跨城市、跨领域的效果泛化仍需系统评测。

### 4.3 现有校验机制及其边界

| 校验位置 | 已实现行为 | 能证明什么与不能证明什么 |
| --- | --- | --- |
| 回归测试 | 覆盖地址、提取、输出等已知规则；“省实路”有对应修复用例 | 证明当前实现通过所覆盖的用例，不证明任意输入均正确 |
| 基础教育 `preview` | 对已登记来源与提取规则进行行覆盖、重叠和待批准检查 | 是独立命令，协议要求通过后提取；`extract` 不自动验证此前已通过预览，也不证明网上未遗漏其他来源 |
| 公共 `extract` | 检查来源复核状态，执行 `approved=true` 的规则 | 检查批准标记和规则执行错误，不独立判断 Agent 的语义批准是否正确 |
| 高校覆盖检查 | 核对种子名单内学校的域名、抓取与结果覆盖，设置页面预算和校区覆盖提示 | 针对给定名单与已发现证据，不是所有实际校区的完整性证明 |
| 医疗 `medical_quality_check.py` | 检查缺失行政单位、ready 来源、平台记录数一致性、交付数量下界及大类缺失 | 独立命令，由协议要求交付前执行；`build_excel.py` 不自动调用 |
| 高校 `build_excel.py` | 生成前检查联系词残留、同路有门牌与无门牌的特定重复，命中直接抛错 | 属于生成入口内的阻断，覆盖的是已编码问题，不是全面语义质量判断 |

医疗数量下界默认是整理后主表记录数不低于平台记录数的 90%，不是准确率、召回率或演进提升比例。多执业地址拆分、去重、物理区分桶及补充来源都会影响分子。类别阻断默认针对平台计数至少 10 条而交付为零的大类，并允许清单中的 `no_official_source` 类别声明豁免；声明理由的真实性仍需语义复核。代码中 `has_ready_full_source` 实际仅检查是否存在 ready 来源，不能自动证明该来源确为全量名录。

演进效果评测还需增加：固定任务与来源快照、明确的标注和评分、旧版与新版对照，以及未参与修改的测试任务。现有质量报告不能替代这一层。

### 4.4 真实演进案例

| 触发场景 | 暴露的问题 | 演化动作 | 沉淀位置 |
| --- | --- | --- | --- |
| 基础教育 | 政府名录形态异构（网页/Excel/Word/PDF/zip/GBK） | 各类读取器、栏目链接、来源文件下载与 zip 安全解压收编为公共能力 | 核心 `official/readers`、`official/collectors` |
| 基础教育 | 扫描件解析服务与凭据配置需要调整 | 接入 MinerU v4 API 逐页解析，凭据读 .env/环境变量，沿用 `vision_source_result` 格式 | 核心 `mineru_reader` + 教育脚本 |
| 基础教育→医疗 | inspect/extract 规则推理带学校语义，难以复用 | 抽成通用引擎，场景词表经 `FieldTerms` 注入，业务构造由回调处理 | 核心 `official/extract` |
| 医疗接入 | 自研解析器与教育链路重复 | 删除自研实现，统一走公共 inspect/extract 与统一阶段文件 | 医疗 Skill + 公共链路 |
| 医疗 | 在线注册平台无法用静态附件覆盖，平台口径复杂 | 新增 `platform-query` 分页采集（来源形态通用，医疗首个落地）；90% 数量下界质量闸门 | 医疗 Skill + `medical_quality_check.py` |
| 高校 | 首页命中地址即停止，漏掉校区/详情地址 | v2.2 白名单链接继续补抓、页面预算扩展、`campus_coverage` 覆盖告警 | 高校 Skill + 核心采集器 |

## 5. 扩展到其它检索场景

### 5.1 扩展的决策入口：先判断来源形态，再选模板

- **政府公开名单/附件、按行政单位交付** → 用政府名单型模板（现教育、医疗实例）。核心复用 `official` 读取与提取、`address.process`、Excel 生成；Skill 层新增：来源口径与层级规则、领域词表（`FieldTerms`）、记录构造/拆分/去重逻辑、references schema。
- **先有固定名单/种子、再逐官网取证** → 用 web_search 型模板（现高校实例）。核心复用域名探测、页面抓取、地址处理；Skill 层新增：名单筛选、域名确认口径、单页语义提取、校区/对象规则。
- **混合形态（名单 + 在线平台 + 官网）** → 主模板 + 按需组合，例如医疗在政府名单型之上首次落地平台分页抓取（`platform-query`；同类来源形态教育也可能遇到）。

> 说明：“分页/平台”是来源形态。静态来源可通过教育/医疗共用的 `list-links`、`download`、`collect-details` 处理，分页网址由清单显式登记；这不等于采集器能自动遍历任意分页网站。动态查询平台的分页接口（JSONP、按行政单位过滤、记录数校验）当前只在医疗 Skill 以 `query_platform`/`platform-query` 落地，尚未下沉公共层与模板。同型平台在新场景出现时，需要先核对接口与业务口径，再判断哪些部分可以抽取复用。

### 5.2 新建一个场景 Skill 的清单

1. `SKILL.md`：写清领域口径（哪些对象算、哪些不算）、来源层级与回退、覆盖要求、完成检查、最终回复格式。
2. `references/`：登记阶段 JSON 字段与来源格式约定，并明确哪些校验由脚本完成、哪些由 Agent 复核。
3. `scripts/`：领域词表、来源适配、记录构造/拆分/去重、命令入口、工作簿业务适配与相关测试；复用已具备的公共能力。
4. `assets/`：按需配置官方静态名单，并说明名单版本与覆盖边界。
5. `requirements.txt`：声明公共包版本；另按运行条件确认第三方库、浏览器、外部工具和服务配置。

直接复用的公共能力：城市与下级行政单位上下文、官方来源读取与收集、通用提取引擎、地址规范化与地图验证、网页抓取与域名探测、统一工作簿输出、同主机节流与访问审计。

### 5.3 反哺机制

建议新场景先在自身 Skill 内验证新能力，再依据实际复用需求抽取公共部分。“出现第二个使用场景”是一个实用判断依据，不是代码自动执行的迁移规则：

- 政府查询平台分页（`platform-query`）由医疗场景首次落地；能力本身与来源形态通用，是否下沉公共层/模板取决于第二个需要它的场景；
- 通用提取引擎先服务教育，再被医疗复用；
- `address_equivalence_key`、`address_mode` 等由多场景重复实现收敛为公共字段/函数。

未来候选场景（举例示意，不构成项目承诺）：养老服务机构、托育机构、医保定点医药机构、公共文化场馆等城市设施名录（政府名单型）；博物馆/纪念馆等官网地址取证（web_search 型）。新增 Skill 仍需词表、协议、格式约定、业务适配与测试。模板和公共层的预期收益是减少重复建设；新增代码量、适配耗时和任务质量应实际统计后再报告。

### 5.4 当前边界与未来方向

如实说明，便于答辩中被追问时给出清晰回答：

- **代码已实现**：三场景任务链路、共享公共组件、阶段文件、相关回归测试及分场景质量检查；已确认广州三场景运行产物。
- **协作实践已有证据**：根据真实问题修改协议与代码、抽取公共能力、补充相关用例和文档；历史提交可追溯这些资产变化。
- **尚未实现或尚未验证**：
  - 失败收集、技能提案、候选构建、验证集评测与自动取舍组成的统一演进控制回路；
  - 运行期技能检索、冲突检测、淘汰和自动版本选择；
  - 独立 Skill 之间的自动组合编排（目前主要是函数与脚本复用）；
  - 公共层彻底去除场景适配残留，以及所有协议检查统一接入强制流水线；
  - 跨城市、跨场景的固定评测集和版本对照，量化质量、覆盖、耗时、调用成本与人工干预变化。

当前文档一致性还有一处需另行处理：基础教育 `SKILL.md` 完成检查写“空地址记录不进工作簿”，但同文件输出说明及 `build_excel.py` 会把空地址记录放入异常校表。准确口径应为“不进学校信息主表，保留在 processed 文件与异常校表”。本次仅修订设计总结，未改动该 Skill。

## 6. PPT 素材映射与推荐表述

- **背景第一页（2023）**：区分语言经验积累（Reflexion、ExpeL）与可执行技能积累（Voyager）。按载体分组时标注“按方法分组”，避免用实线箭头暗示 ExpeL 先于 Voyager。按时间展示时则用 Reflexion（3 月）、Voyager（5 月）、ExpeL（8 月）的顺序。
- **背景第二页（2025—2026）**：SkillWeaver 重点是网站技能 API 的合成与测试打磨；EvoSkill 重点是依据验证集得分筛选候选 Agent program。前者也开展整体任务评测，不能概括成只做轨迹级评价。推荐对应标签为“API 合成与可靠性检查”和“验证集驱动的程序选择”。
- **项目架构页**：第 3 节的 Skill 资产、公共核心与模板文档；把 Agent 放在执行链路的组织者位置，将已实现模块与预留模式分开标记。
- **演进机制页**：第 4 节的人机协同流程；明确问题诊断、资产修改与保留判断的参与者，选一个有修复代码与测试的案例展示。
- **发展与证据页**：第 4.5 节提交里程碑、广州产物及针对性测试结果。目录与提交证明工程演化，性能曲线需要另做版本对照。
- **扩展页**：第 5 节模板选择、场景适配与公共层反哺；把自动演进控制器和跨任务效果评测标为未来方向。

项目推荐定位句：

> 面向城市资源检索，形成任务反馈驱动的 Skill 人机协同演进流程，将实际问题沉淀为可复用协议、处理脚本和公共组件，并以回归测试与交付检查约束改动质量。

论文背景推荐衔接句：

> 这些工作展示了语言经验积累、可执行技能构建，以及验证反馈驱动的技能优化等不同路径；本项目探索其中的工程落地与人机协同实践。
